Brainstorm — toward a true per-trade comparison

Captured here per the owner's request to "properly brainstorm and look into the concept architecture and setup for this" — kept as a living note, not a committed roadmap item yet. Full version lives in PLAN.md.

  • What v1 has: live side uses pyquant_signals (every real signal PyQuant opened/closed, with realized_pnl_pct). Backtest side uses pyquant_runs.metrics — aggregate numbers only (Total Return (%), Win Rate (%), Total Trades) from whichever walkforward run finished last.
  • What's missing for per-trade matching: walkforward.py's run_walk_forward() already builds an all_trades list internally (entry/exit price, side, PnL, timestamp per simulated trade) — it's just never persisted past the in-memory return value. A per-trade comparison needs a new pyquant_backtest_trades table (run_id FK, symbol, side, entry/exit price+time, pnl_pct) populated from that same list at save time, mirroring how pyquant_signals already works for the live side.
  • Matching strategy once that exists: not a 1:1 trade-id match (the UKF signal model is deterministic given the same inputs, but live ticks on a 5-minute cadence against real-time bars while the backtest walks fixed historical windows — timestamps won't line up exactly). The practical approach: bucket both sides by calendar day (or week) and compare trade count / win rate / avg return per bucket, which tolerates the timing skew while still being far more granular than one whole-history number each.
  • Why this is v2, not now: it's a real schema addition (pyquant_backtest_trades) plus a walkforward.py change to persist all_trades — exactly the kind of thing that should follow, not block, getting the aggregate version (this page) out and the Kaggle-manual-trigger path (Backtest page's "Sync to Kaggle") working first.
